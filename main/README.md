# Календарь

Веб-приложение «Календарь» на Django 5.2: месячная сетка, события с цветами, перенос перетаскиванием, поиск.

## Запуск

```bash
python -m venv .venv
source .venv/bin/activate        # Windows: .venv\Scripts\activate
pip install -r requirements.txt
python manage.py migrate
python manage.py createsuperuser   # резервный локальный администратор; остальные входят через Active Directory
python manage.py runserver
# синхронизация внешних календарей по расписанию: python manage.py sync_calendars (см. INTEGRATIONS.md)
```

Откройте http://127.0.0.1:8000/ и войдите с учётной записью домена (см. [«Вход через Active Directory»](#вход-через-active-directory)). Админка — `/admin/`.

Тесты: `python manage.py test events models_employee integrations directory`

Запуск в Docker: `docker compose up -d --build` из каталога `main` — см. [ADMIN_GUIDE.md](ADMIN_GUIDE.md), раздел «Запуск в Docker».

## Возможности

- Три вида календаря — выпадающий список «Месяц / Неделя / День» в шапке (выбор запоминается в браузере):
  - **Месяц** — сетка 6×7 (неделя с понедельника), подсветка сегодняшнего и выбранного дня, выходные;
  - **Неделя** и **День** — почасовая сетка: строка «весь день» для многодневных событий, пересекающиеся события встают рядом, красная линия текущего времени. Двойной клик по часу — новое событие на это время, клик по заголовку дня в «Неделе» открывает «День».
- Стрелки ‹ › листают месяц, неделю или день в зависимости от вида.
- Панель выбранного дня со списком событий: время, место, описание.
- Создание, редактирование и удаление событий в модальном окне: название, весь день, начало/окончание, место, ссылка, приглашённые, цвет, описание, файлы. При изменении начала окончание сдвигается с сохранением длительности.
- **Ссылка** на веб-ресурс (Zoom, документ, сайт). Если схема не указана, подставляется `https://`.
- **Приглашённые** — множественный выбор из активных пользователей Django с поиском по имени и e-mail; управление клавиатурой (↑/↓, Enter, Backspace удаляет последнего). Пользователей добавляют в админке (`/admin/auth/user/`).
- **Файлы** — несколько вложений к событию: кнопка выбора или перетаскивание, до 20 МБ на файл и до 20 файлов на событие. Файлы хранятся в `media/attachments/` и всегда отдаются как скачивание. Удаление события удаляет и его файлы.
- Многодневные события и события «на весь день» отображаются как плашки на каждом дне.
- Перенос события перетаскиванием: на другой день (в «Месяце») или на другое время с шагом 15 минут (в «Неделе» и «Дне»).
- Поиск по названию, месту и описанию.
- Горячие клавиши: `←` / `→` — назад/вперёд, `M` / `W` / `D` — месяц/неделя/день, `T` — сегодня, `N` — новое событие, `/` — поиск, `Esc` — закрыть.
- Тёмная тема (по настройке системы), адаптивная вёрстка для телефона.

**Инструкции: [пользователя](USER_GUIDE.md), [администратора](ADMIN_GUIDE.md), [по API](API.md).** Схема приложения — `shema.drawio` в корне репозитория.

**Внешние календари (Microsoft Exchange, Google, Яндекс, Mail.ru, Рамблер) и приглашения по e-mail — в [INTEGRATIONS.md](INTEGRATIONS.md). Адресная книга из Active Directory / LDAP — в [DIRECTORY.md](DIRECTORY.md).**

## Роли и права (пакет `models_employee`)

Вход обязателен (`/accounts/login/`) — по учётной записи домена Active Directory. Действия:

- **Запись** — создание новых событий в календаре владельца;
- **Чтение** — просмотр событий со всеми подробностями (описание, место, ссылка, участники, файлы);
- **Изменение** — редактирование, перенос и удаление событий и их файлов. Изменение включает чтение.

Роли **не взаимоисключающие**: один сотрудник может быть владельцем своего календаря, менеджером календаря руководителя, наблюдателем и администратором одновременно. Итоговые права — объединение прав всех его ролей.

| Роль | Как получить | Запись | Чтение | Изменение |
|---|---|---|---|---|
| Владелец | флаг `is_owner`, по умолчанию у всех | в своём календаре | свои события | свои события |
| Менеджер | владелец выдаёт права (шестерёнка → «Доступ»); можно быть менеджером нескольких календарей; пользователи из `CALENDAR_MANAGERS` — менеджеры всех календарей с правом чтения | если делегировано | если делегировано | если делегировано |
| Наблюдатель | флаг `is_observer` | — | все события | все события |
| Администратор | флаг `is_admin`, у суперпользователя всегда | в любом календаре | все события | все события |

Владелец делегирует права **каждому действию отдельно**, любому другому сотруднику — на весь календарь (шестерёнка → «Доступ») или на одно событие (в админке). Администратор управляет ролями (шестерёнка «Настройки» → «Роли сотрудников» → админка, раздел «Сотрудники»), может сменить владельца события. Любой приглашённый на событие может его прочитать. Событие без права чтения пользователю не видно.

- Флаги ролей — в модели `Employee` (профиль создаётся автоматически). Значения для новых пользователей — `EMPLOYEE_DEFAULT_IS_OWNER` / `EMPLOYEE_DEFAULT_IS_OBSERVER` в настройках.
- Делегирование — модель `Delegation` (владелец → сотрудник, флаги «Запись / Чтение / Изменение», необязательное событие).
- Вся проверка прав — `models_employee/permissions.py` (класс `Access`).

В окне «Доступ» сотрудника ищут по фамилии, имени (в любом порядке), e-mail или логину: подсказки появляются по мере ввода, лучшие совпадения — первыми, полное совпадение помечено. Регистр не важен, «ё» = «е».

API делегирования: `GET /api/delegations/candidates/?q=текст` — подсказки (до 10), `GET /api/delegations/` — кому выданы права, `POST /api/delegations/` `{"manager": id, "can_create": bool, "can_read": bool, "can_change": bool}` (все false — права отозваны).

## Вход через Active Directory

Пользователи входят с логином и паролем домена `yanao.ru`: `ivanov` или `ivanov@yanao.ru`. Пароль проверяет сервер домена — календарь подключается к нему по LDAP **от имени входящего пользователя** (служебная учётная запись не нужна) и читает его запись. Пароли в базе календаря не хранятся, смены и сброса пароля в календаре нет.

- При первом входе создаётся пользователь календаря с ролью «Владелец»; при каждом входе из домена обновляются имя, фамилия, e-mail (`mail`) и должность (`title`). Пустые значения из домена не затирают заполненное в календаре.
- Пользователь привязан к записи домена по `objectGUID`: переименование логина в домене сохраняет календарь, а повторно выданный логин не получает чужой календарь (вход отклоняется — привязку решает администратор).
- Отключённые, заблокированные и просроченные учётные записи войти не могут; причину, которую сообщил домен (пароль истёк, запись заблокирована), видно на странице входа. Отключить сотрудника только в календаре — снять флаг «Активный» у пользователя в админке.
- **Резервный вход**: локальные суперпользователи (`python manage.py createsuperuser`) входят по паролю из базы календаря, даже когда домен недоступен. Остальные локальные пароли не действуют.
- Неудачные попытки входа учитываются политикой блокировки домена.
- Открытая сессия живёт до выхода или `SESSION_COOKIE_AGE` (по умолчанию в Django — 2 недели): отключение записи в домене не завершает уже открытую сессию.

Настройки — в `main/settings.py` (переменные окружения с теми же именами) или в `main/local_settings.py` (настройки машины, не хранится в git):

| Настройка | По умолчанию | Пояснение |
|---|---|---|
| `AD_AUTH_DOMAIN` | `yanao.ru` | имя домена: суффикс логина (`ivanov@yanao.ru`). Пусто — вход через домен выключен |
| `AD_AUTH_SERVERS` | `email.yanao.ru` | серверы домена через запятую (второй — резерв). Пусто — имя домена |
| `AD_AUTH_SECURITY` | `ssl` | `ssl` — LDAPS (636), `starttls` — StartTLS (389), `none` — без шифрования (пароль открытым текстом, не используйте) |
| `AD_AUTH_VERIFY_CERT` | включено | проверка сертификата контроллера домена; серверы при этом указываются по именам, а не по IP |
| `AD_AUTH_CA_CERT_FILE` | | корневой сертификат центра сертификации домена (`.pem`), если его нет в доверенных на сервере календаря |
| `AD_AUTH_BASE_DN` | `cn=yg.loc` | где искать запись пользователя. Пусто — из имени домена (`DC=yanao,DC=ru`) |
| `AD_AUTH_REQUIRE_GROUP` | | войти могут только члены группы (DN или имя; вложенные группы учитываются). Пусто — любой пользователь домена |
| `AD_AUTH_ADMIN_GROUP` | | члены группы получают роль «Администратор» при входе, вышедшие из группы — теряют. Пусто — роль назначается только в админке |
| `AD_AUTH_ADMIN_USERS` | | логины через запятую (`ivanov` или `ivanov@yanao.ru`) — роль «Администратор» при каждом входе, независимо от группы |
| `CALENDAR_MANAGERS` | | логины через запятую (`ivanov` или `ivanov@yanao.ru`) — роль «Менеджер» и чтение событий всех календарей |

Основная группа пользователя (обычно «Пользователи домена») в проверке групп не учитывается — это особенность Active Directory.

**Домен yanao.ru.** У домена нет собственных контроллеров в DNS: учётные записи `логин@yanao.ru` проверяет LDAP-сервер `email.yanao.ru` (LDAPS, порт 636), за которым стоит каталог Active Directory `yg.loc`; его корень на этом сервере называется `cn=yg.loc`. Сертификат сервера публичный, проверка включена (имя сервера передаётся в SNI — без него сервер отдаёт другой сертификат). Особенности этого сервера: запись пользователя ищется по логину (`sAMAccountName`), он совпадает с именем почтового ящика; группы в `AD_AUTH_REQUIRE_GROUP` / `AD_AUTH_ADMIN_GROUP` задаются только полным DN в том виде, как в атрибуте `memberOf` (`CN=…,DC=yg,DC=loc`), и учитывается только прямое членство — поиск групп по имени и вложенные группы сервер не поддерживает; причину отказа (пароль истёк, запись заблокирована) сервер не сообщает — пользователь видит «Неверное имя пользователя или пароль».

Чтобы вернуться к обычному домену Active Directory (например, `zs.int`), задайте `AD_AUTH_DOMAIN`, укажите контроллеры в `AD_AUTH_SERVERS` и очистите `AD_AUTH_BASE_DN`. Пользователь календаря привязан к записи того домена, через который вошёл: после смены домена сотрудник входит как новый пользователь.

Проверка из командной строки (пользователь календаря не создаётся):

```bash
python manage.py ad_auth_check ivanov        # спросит пароль; покажет DN, objectGUID, имя, e-mail, должность
python manage.py ad_auth_check --diagnose    # DNS и доступность LDAP-портов, без входа
```

Тесты входа (без обращения к домену): `python manage.py test models_employee.tests_ad_auth`.

## JSON API

| Метод | URL | Описание |
|---|---|---|
| GET | `/api/events/?start=YYYY-MM-DD&end=YYYY-MM-DD` | события, пересекающиеся с диапазоном `[start, end)` |
| GET | `/api/events/?q=текст` | поиск |
| POST | `/api/events/` | создать |
| GET / PUT / PATCH / DELETE | `/api/events/<id>/` | получить / заменить / изменить часть / удалить |
| POST | `/api/events/<id>/attachments/` | загрузить файлы (multipart, поле `files`, можно несколько) |
| DELETE | `/api/attachments/<id>/` | удалить вложение |
| GET | `/api/attachments/<id>/download/` | скачать вложение |

Даты передаются как `YYYY-MM-DDTHH:MM` в часовом поясе `TIME_ZONE`. Запросы на изменение требуют CSRF-токен (заголовок `X-CSRFToken`, cookie ставится на главной странице).

Пример тела:

```json
{"title": "Встреча", "start": "2026-10-12T10:00", "end": "2026-10-12T11:30",
 "all_day": false, "color": "green", "location": "Офис", "description": "",
 "url": "https://meet.example.com/abc", "invitees": [1, 3]}
```

В ответе `invitees` — список `{"id", "name"}`, `attachments` — список `{"id", "name", "size", "url"}`.

Цвета — 24 значения, список в [API.md](API.md#объект-событие).

## Настройки (шестерёнка)

Кнопка с шестерёнкой рядом с «Выйти» открывает настройки:

- **Мой календарь** (владельцу календаря) — «Доступ» (права менеджеров) и «Интеграции» (внешние календари);
- **Отчет по событиям** — период «С / По» (по умолчанию — открытый в календаре месяц) и кнопка «Отчет»: скачивается файл «Отчет по событиям.docx» со всеми событиями, которые пользователь видит в календаре, за выбранный период (формируется в `events/report.py`, без сторонних библиотек);
- **Оформление** — как в системе, светлое или тёмное;
- **Вид при открытии календаря** — последний выбранный, «Месяц», «Неделя» или «День»;
- **Администрирование** (только администратору) — ссылки на роли сотрудников, адресную книгу AD/LDAP, почтовый сервер, внешние календари и всю админку.

Оформление и вид — **личные настройки каждого пользователя**: хранятся на сервере (`Employee.preferences`), не зависят от браузера и компьютера и не влияют на других пользователей. API — `GET/PATCH /api/me/settings/` (см. API.md).

## Форма события

Поля: **Тема**, «Весь день», **Начало** и **Окончание**, **Где**, **Участники**, **Напоминание**, «Отправить приглашения по e-mail», цвет, описание, файлы.

- **Участники** — выбор людей из адресной книги Active Directory / LDAP (поиск по фамилии, имени, e-mail; ↑/↓, Enter). Выбранные из адресной книги автоматически получают событие в свой календарь (см. INTEGRATIONS.md). Внешний адрес, которого нет в адресной книге, можно добавить, введя его целиком и нажав Enter (пунктирная рамка). Сотрудники с учётной записью в календаре видят событие и у себя.
- **Напоминание** — за сколько до начала напомнить (по умолчанию для нового события — за 15 минут). Напоминание показывается в открытом календаре (всплывающее уведомление браузера и сообщение внизу экрана), передаётся в Exchange — Outlook напомнит сам, и в приглашения `.ics`.
- Поля «Ссылка» в форме нет; ссылка, пришедшая из других календарей или через API, сохраняется.

## 1. Состав приложения

Проект Django 5.2 (Python 3.11 и новее), каталог `main/`.

| Приложение | Назначение |
|---|---|
| `main` | настройки (`settings.py`), адреса (`urls.py`), точки входа WSGI/ASGI |
| `models_employee` | вход через домен, роли, делегирование прав, личные настройки |
| `events` | события, файлы, отчёт `.docx`, страница календаря и её API |
| `integrations` | синхронизация с внешними календарями, приглашения по почте |
| `directory` | адресная книга: поиск на сервере Active Directory / LDAP |

Данные:

| Что | Где |
|---|---|
| база данных | `main/db.sqlite3` (SQLite) |
| файлы событий | `main/media/attachments/` |
| настройки машины | `main/.env`, `main/main/local_settings.py` — в git не хранятся |

Внешние системы, к которым обращается сервер календаря: LDAP-сервер домена (вход и адресная книга), почтовый сервер SMTP (приглашения), Exchange / CalDAV / Google (календари пользователей).

## 2. Установка и запуск

```bash
cd main
python -m venv ../.venv
source ../.venv/bin/activate          # Windows: ..\.venv\Scripts\activate
pip install -r requirements.txt
cp .env.example .env                  # и заполните, см. раздел 3
python manage.py migrate
python manage.py createsuperuser      # резервный локальный администратор
python manage.py runserver 0.0.0.0:8000
```

Откройте `http://<адрес сервера>:8000/`. Админка — `/admin/`.

- Адрес, по которому открывают календарь, должен быть перечислен в `DJANGO_ALLOWED_HOSTS`, иначе сервер ответит «Bad Request (400)».
- `runserver` — сервер разработки. Для постоянной работы запускайте приложение под WSGI-сервером (точка входа — `main.wsgi:application`) за веб-сервером, с `DJANGO_DEBUG=0`. При `DEBUG=0` Django сам не отдаёт статику: выполните `python manage.py collectstatic` (файлы соберутся в `main/staticfiles/`) и настройте веб-сервер отдавать `/static/` из этого каталога. Файлы событий через веб-сервер отдавать не нужно — они выдаются только через API с проверкой прав.
- После изменения `.env` или `local_settings.py` сервер нужно перезапустить: настройки читаются при старте.

Проверка установки: `python manage.py check` и `python manage.py test` (тесты не обращаются к домену и внешним серверам, занимают несколько минут).

### Запуск в Docker

В каталоге `main` лежат `Dockerfile` и `docker-compose.yml`. В образе приложение работает под gunicorn, статику отдаёт само (отдельный веб-сервер для `/static/` не нужен), плановая синхронизация внешних календарей запускается внутри контейнера.

```bash
cd main
cp .env.example .env                  # и заполните, см. раздел 3
docker compose up -d --build
docker compose run --rm calendar python manage.py createsuperuser   # резервный локальный администратор
```

Без Docker Compose — то же двумя командами:

```bash
docker build -t calendar .
docker run -d --name calendar --restart unless-stopped --env-file .env -e DJANGO_DEBUG=0 \
    -p 8000:8000 -v calendar-data:/data calendar
```

- **Данные** — в томе `calendar-data` (в контейнере `/data`): база `db.sqlite3` и файлы событий `media/`. Том переживает пересоздание контейнера; при каждом запуске выполняется `migrate`.
- **Настройки** — из файла `.env`, он передаётся контейнеру при запуске и в образ не попадает. Обязательно задайте `DJANGO_SECRET_KEY` и перечислите адрес сайта в `DJANGO_ALLOWED_HOSTS`. С `docker run --env-file` значения пишите без кавычек. Файл `local_settings.py` в образ не попадает.
- **HTTPS.** Контейнер отвечает по HTTP на порту 8000 — поставьте перед ним обратный прокси с сертификатом (nginx и т. п.) и задайте `DJANGO_BEHIND_PROXY=1` и `DJANGO_CSRF_TRUSTED_ORIGINS=https://адрес-сайта`. Прокси должен передавать заголовки `X-Forwarded-Proto` и `X-Forwarded-Host`.
- **Синхронизация** — `sync_calendars` выполняется каждые `SYNC_INTERVAL_MINUTES` минут (по умолчанию 10); `0` — не выполнять. Задание cron из раздела 9 в этом случае не нужно.
- **Сертификат центра сертификации домена** (`AD_AUTH_CA_CERT_FILE`) положите в том или подключите файлом: `-v /путь/ca.pem:/data/ca.pem:ro` и `AD_AUTH_CA_CERT_FILE=/data/ca.pem`.
- **Перенос существующей базы:** при остановленном контейнере скопируйте `db.sqlite3` и каталог `media` в том, владелец файлов — пользователь с uid 1000 (под ним работает приложение).
- **Команды управления:** `docker compose exec calendar python manage.py <команда>` (например, `ad_auth_check`, `sync_calendars`).
- **Обновление:** `git pull && docker compose up -d --build`. **Резервная копия:** `docker compose exec calendar python -c "import sqlite3; sqlite3.connect('/data/db.sqlite3').backup(sqlite3.connect('/data/backup.sqlite3'))"`, затем заберите `/data/backup.sqlite3` и `/data/media`.
- Контейнер запускает один процесс gunicorn с несколькими потоками — не увеличивайте число процессов (`--workers`): блокировки отправки событий и кэш адресной книги живут в памяти процесса.

## 3. Настройки

Настройки задаются переменными окружения; удобнее всего — в файле `main/.env` (образец — `.env.example`). Переменная, уже заданная в окружении, из файла не перезаписывается. Значения, которые нельзя выразить переменной, можно переопределить в `main/main/local_settings.py`.

### Django

| Переменная | По умолчанию | Назначение |
|---|---|---|
| `DJANGO_SECRET_KEY` | встроенный ключ для разработки | секретный ключ. **На рабочем сервере задайте свой** |
| `DJANGO_DEBUG` | `1` | `0` на рабочем сервере |
| `DJANGO_ALLOWED_HOSTS` | `localhost,127.0.0.1` | имена и адреса, по которым открывают календарь, через запятую |

Новый ключ: `python -c "from django.core.management.utils import get_random_secret_key as k; print(k())"`.

### Вход через домен

| Переменная | По умолчанию | Назначение |
|---|---|---|
| `AD_AUTH_DOMAIN` | `yanao.ru` | домен учётных записей (суффикс логина). Пусто — вход через домен выключен |
| `AD_AUTH_SERVERS` | `email.yanao.ru` | серверы домена через запятую, второй — резерв |
| `AD_AUTH_SECURITY` | `ssl` | `ssl` — LDAPS (636), `starttls` — StartTLS (389), `none` — без шифрования (не используйте) |
| `AD_AUTH_PORT` | `0` | `0` — 636 для `ssl`, иначе 389 |
| `AD_AUTH_VERIFY_CERT` | `1` | проверять сертификат сервера |
| `AD_AUTH_CA_CERT_FILE` | | корневой сертификат (`.pem`), если его нет в доверенных на сервере календаря |
| `AD_AUTH_BASE_DN` | `cn=yg.loc` | где искать запись пользователя |
| `AD_AUTH_REQUIRE_GROUP` | | войти могут только члены группы. Пусто — любой пользователь домена |
| `AD_AUTH_ADMIN_GROUP` | | члены группы получают роль «Администратор» при входе, вышедшие — теряют |
| `AD_AUTH_ADMIN_USERS` | | логины через запятую — роль «Администратор» при каждом входе |
| `CALENDAR_MANAGERS` | | логины через запятую — роль «Менеджер» с чтением всех календарей |

### Внешние календари и почта

| Переменная | По умолчанию | Назначение |
|---|---|---|
| `INTEGRATIONS_ENCRYPTION_KEY` | выводится из `DJANGO_SECRET_KEY` | ключ шифрования паролей и токенов в базе |
| `INTEGRATIONS_EXCHANGE_URL` | `https://email.yanao.ru/EWS/Exchange.asmx` | адрес Exchange по умолчанию при подключении календаря |
| `INTEGRATIONS_UID_DOMAIN` | `calendar.local` | домен в идентификаторах событий, которые календарь создаёт во внешних календарях |
| `INTEGRATIONS_MAIL_FROM_USER` | `0` | `1` — приглашения от адреса автора события, см. [раздел 7](#7-почтовый-сервер-и-приглашения) |
| `GOOGLE_OAUTH_CLIENT_ID`, `GOOGLE_OAUTH_CLIENT_SECRET` | | ключи для подключения Google Календаря |
| `EMAIL_HOST`, `EMAIL_PORT`, `EMAIL_HOST_USER`, `EMAIL_HOST_PASSWORD`, `EMAIL_USE_SSL`, `EMAIL_USE_TLS`, `DEFAULT_FROM_EMAIL` | | почта через переменные окружения — используется, только если почтовый сервер не задан в админке |

Остальное задаётся прямо в `main/settings.py`: часовой пояс (`TIME_ZONE`, сейчас `Asia/Yekaterinburg`), окно синхронизации (`INTEGRATIONS_SYNC_PAST_DAYS` = 30, `INTEGRATIONS_SYNC_FUTURE_DAYS` = 365), предел файлов в письме (`INTEGRATIONS_MAIL_MAX_ATTACHMENTS_MB` = 20), роли новых пользователей (`EMPLOYEE_DEFAULT_IS_OWNER`, `EMPLOYEE_DEFAULT_IS_OBSERVER`), параметры адресной книги (`DIRECTORY_TIMEOUT`, `DIRECTORY_CACHE_SECONDS`).

## 4. Вход через домен

Пользователи входят с логином и паролем домена. Пароль проверяет LDAP-сервер: календарь подключается к нему от имени входящего пользователя и читает его запись. Служебная учётная запись для входа не нужна, пароли в базе календаря не хранятся.

- При первом входе создаётся пользователь календаря с ролью «Владелец»; при каждом входе обновляются имя, фамилия, e-mail и должность.
- Пользователь привязан к записи домена по `objectGUID`: переименование логина сохраняет календарь, а повторно выданный логин не получает чужой календарь (вход отклоняется, привязку решает администратор).
- Смены и сброса пароля в календаре нет.
- Открытая сессия действует до выхода или две недели: отключение учётной записи в домене не завершает уже открытую сессию. Чтобы закрыть доступ сразу, снимите у пользователя флаг «Активный» в админке.

**Домен yanao.ru.** Учётные записи проверяет сервер `email.yanao.ru` (LDAPS, порт 636), за которым стоит каталог Active Directory `yg.loc`; его корень на этом сервере — `cn=yg.loc`. Особенности:

- группы в `AD_AUTH_REQUIRE_GROUP` и `AD_AUTH_ADMIN_GROUP` задаются только полным DN в том виде, как в атрибуте `memberOf` (`CN=…,DC=yg,DC=loc`); учитывается только прямое членство;
- причину отказа (пароль истёк, запись заблокирована) сервер не сообщает — пользователь видит «Неверное имя пользователя или пароль»;
- сертификат сервера публичный, проверка включена.

**Резервный вход.** Локальные суперпользователи (`createsuperuser`) входят по паролю из базы календаря, даже когда домен недоступен. Держите хотя бы одну такую учётную запись. Остальные локальные пароли не действуют.

Проверка из командной строки (пользователь календаря не создаётся и не меняется):

```bash
python manage.py ad_auth_check --diagnose    # DNS и доступность LDAP-портов, без входа
python manage.py ad_auth_check ivanov        # спросит пароль; покажет DN, objectGUID, имя, e-mail, должность
```

Смена домена: задайте `AD_AUTH_DOMAIN`, `AD_AUTH_SERVERS`, `AD_AUTH_BASE_DN` и перезапустите сервер. Пользователь привязан к записи того домена, через который вошёл: после смены домена сотрудник входит как новый пользователь, его прежние события остаются у прежней учётной записи.

## 5. Пользователи и роли

Роли складываются — у одного сотрудника их может быть несколько.

| Роль | Права | Как назначается |
|---|---|---|
| Владелец | свой календарь: запись, чтение, изменение, выдача прав | флаг «Владелец», по умолчанию у всех |
| Менеджер | чужой календарь в пределах выданных прав | владелец выдаёт права сам (шестерёнка → «Доступ»); либо логин в `CALENDAR_MANAGERS` — чтение всех календарей |
| Наблюдатель | чтение и изменение всех событий, без создания | флаг «Наблюдатель» |
| Администратор | всё во всех календарях, вход в админку | флаг «Администратор», `AD_AUTH_ADMIN_USERS`, `AD_AUTH_ADMIN_GROUP`; суперпользователь — всегда |

Где управлять (админка → раздел **«Сотрудники и роли»**; быстрые ссылки — в календаре: шестерёнка → «Администрирование»):

- **«Сотрудники»** — флаги ролей и должность. Колонка «Менеджер календарей» показывает, чьими календарями управляет сотрудник.
- **«Делегирование прав»** — кто кому выдал права. Здесь же можно выдать права **на одно событие** (в окне «Доступ» пользователь выдаёт права только на весь календарь).
- **«Пользователи»** — флаг «Активный» (закрыть доступ к календарю), имя, e-mail.

Важно:

- Роль, заданная через `AD_AUTH_ADMIN_USERS` или `AD_AUTH_ADMIN_GROUP`, выставляется заново при каждом входе. Если задана `AD_AUTH_ADMIN_GROUP`, у вышедших из группы роль «Администратор» снимается — включая выданную вручную в админке.
- Сменить владельца события может только администратор: в админке (раздел «Календарь» → «События») или через API.
- Пользователь появляется в календаре только после первого входа. Выдать права сотруднику, который ещё ни разу не входил, нельзя.

## 6. Адресная книга

Адресная книга ищет контакты прямо на сервере каталога при каждом запросе; копии в базе календаря нет. Доступна всем вошедшим пользователям, настраивает её только администратор.

Админка → **«Адресная книга (AD / LDAP)» → «Каталоги (AD / LDAP)» → «Добавить»**:

| Поле | Значение для yanao.ru |
|---|---|
| Тип каталога | LDAP |
| Имя сервера | `email.yanao.ru` |
| Порт | `636` |
| Корневой элемент (Base DN) | `cn=yg.loc` |
| Имя пользователя (Bind DN) | учётная запись для чтения каталога, `логин@yanao.ru` |
| Пароль | хранится зашифрованным |

Кнопки **«Сохранить и проверить подключение»** и **«Сохранить и проверить поиск»** сразу показывают найденные записи, пришедшие атрибуты и причину ошибки. Сертификат этого сервера публичный — проверку сертификата можно оставить включённой.

Проверка из командной строки: `python manage.py directory_check`, `--search Петров`, `--diagnose`. Подробно, включая сопоставление атрибутов и частые ошибки, — в [DIRECTORY.md](DIRECTORY.md).

## 7. Почтовый сервер и приглашения

Без настроенной почты приглашения не отправляются: пользователь после сохранения события видит «Почтовый сервер не настроен».

Админка → **«Внешние календари» → «Почтовый сервер (отправка приглашений)» → «Добавить»**:

| Поле | Значение |
|---|---|
| Сервер SMTP, порт, шифрование | `email.yanao.ru`, `587`, STARTTLS |
| Логин и пароль | учётная запись с почтовым ящиком |
| Адрес отправителя | **тот же адрес, что логин** |

Кнопка **«Сохранить и отправить тестовое письмо»** проверяет настройки и показывает причину ошибки. Последняя ошибка отправки видна в списке почтовых серверов.

**От кого приходят приглашения.** От «Адреса отправителя»; ответы приходят владельцу события. Сервер `email.yanao.ru` не разрешает указывать отправителем адрес, не совпадающий с учётной записью входа: такое письмо принимается, а затем возвращается отправителю с ошибкой «Not allowed address». Поэтому `INTEGRATIONS_MAIL_FROM_USER=1` (письма от адреса автора события) включайте, только если администратор почты разрешил учётной записи календаря отправлять от адресов сотрудников («Отправить как»).

**Кому и что отправляется.** Участникам, выбранным из адресной книги, — автоматически: приглашение, обновление при изменении события или его файлов, отмена. Гостям, вписанным вручную, — если пользователь отметил «Отправить приглашения по e-mail участникам». Файлы события вкладываются в письмо (до `INTEGRATIONS_MAIL_MAX_ATTACHMENTS_MB` в сумме). Что и кому отправлено — админка → «Внешние календари» → **«Доставка участникам»**.

Если у владельца события подключён Exchange, приглашения рассылает сам Exchange от учётной записи владельца.

## 8. Внешние календари

Пользователи подключают свои календари сами (шестерёнка → «Интеграции»). Задачи администратора:

- **Exchange** — проверить `INTEGRATIONS_EXCHANGE_URL`.
- **Google** — создать OAuth-клиент и задать `GOOGLE_OAUTH_CLIENT_ID` / `GOOGLE_OAUTH_CLIENT_SECRET` (порядок — в [INTEGRATIONS.md](INTEGRATIONS.md#google-календарь)). Без них пункт «Google Календарь» виден, но вход недоступен.
- **Плановая синхронизация** — поставить в расписание, см. [раздел 9](#9-регулярные-задачи).

В админке, раздел **«Внешние календари»**:

- «Внешние календари» — подключения пользователей, время и итог последней синхронизации, последняя ошибка; действие «Синхронизировать сейчас».
- «Синхронизированные события» — связи событий с внешними календарями.
- «Доставка участникам» — кому и каким способом доставлено событие.

Пароли и токены подключений хранятся зашифрованными и в админке не показываются.

## 9. Регулярные задачи

Изменения, сделанные во внешних календарях, и приглашения, которые не удалось отправить сразу, забирает и досылает команда `sync_calendars`. Запускайте её по расписанию, например каждые 10 минут:

```
*/10 * * * * cd /путь/к/проекту/main && /путь/к/.venv/bin/python manage.py sync_calendars >> /var/log/calendar-sync.log 2>&1
```

Варианты: `sync_calendars --user ivanov` — календари одного пользователя, `--id 3 --id 5` — выбранные подключения.

Сессии пользователей хранятся в базе; раз в сутки удаляйте просроченные: `python manage.py clearsessions`.

## 10. Резервное копирование и обновление

Что сохранять:

- `main/db.sqlite3` — пользователи, роли, события, подключения, настройки каталогов и почты;
- `main/media/` — файлы событий;
- `main/.env` и `main/main/local_settings.py` — настройки и ключи.

Копию базы делайте при остановленном сервере либо командой `sqlite3 db.sqlite3 ".backup 'копия.sqlite3'"`. База и ключи должны храниться вместе: без `DJANGO_SECRET_KEY` (или `INTEGRATIONS_ENCRYPTION_KEY`) сохранённые пароли подключений, каталогов и почтового сервера не расшифровать.

Обновление:

```bash
cd /путь/к/проекту
git pull
source .venv/bin/activate
cd main
pip install -r requirements.txt
python manage.py migrate
python manage.py collectstatic --noinput    # если статику отдаёт веб-сервер
# перезапустите сервер приложения
```

После обновления пользователям не нужно чистить кэш браузера: адреса скрипта и стилей страницы меняются вместе с файлами.

## 11. Диагностика

| Команда | Что проверяет |
|---|---|
| `python manage.py check` | настройки проекта |
| `python manage.py ad_auth_check --diagnose` | DNS и порты сервера домена |
| `python manage.py ad_auth_check ЛОГИН` | вход конкретного пользователя и данные его записи |
| `python manage.py directory_check [--search ТЕКСТ] [--diagnose]` | адресную книгу |
| `python manage.py exchange_check ID_СОБЫТИЯ [--fix]` | как событие выглядит в Exchange; `--fix` — перезаписать и дослать файлы |
| `python manage.py sync_calendars` | синхронизацию: итог по каждому подключению |

Частые ситуации:

| Признак | Причина и действие |
|---|---|
| Никто не может войти | недоступен сервер домена или не проходит проверка сертификата: `ad_auth_check --diagnose`. Войдите локальным суперпользователем |
| Один пользователь не может войти | пароль, блокировка или срок действия пароля в домене: `ad_auth_check ЛОГИН`. Сообщение на странице входа «Этот логин уже занят в календаре другой учётной записью» означает, что в календаре уже есть пользователь с таким логином — локальный суперпользователь или привязанный к другой записи домена |
| «Bad Request (400)» вместо страницы | адрес не указан в `DJANGO_ALLOWED_HOSTS` |
| Приглашения не приходят | почтовый сервер не настроен или отклоняет вход: тестовое письмо в админке; «Доставка участникам» покажет, отправлялось ли |
| Приглашение вернулось: «Not allowed address» | адрес отправителя не совпадает с учётной записью почтового сервера: исправьте «Адрес отправителя», выключите `INTEGRATIONS_MAIL_FROM_USER` |
| «Каталог временно недоступен» в контактах | `directory_check --diagnose`; причина видна администратору в окне «Контакты» и в списке каталогов |
| Событие не появилось во внешнем календаре | ошибка в карточке подключения (окно «Интеграции» или админка); `sync_calendars` дошлёт |
| После обновления кнопка на странице не работает | у пользователя осталась старая страница: обновить клавишей F5 |
| Настройка из `.env` не действует | сервер не перезапущен, либо значение переопределено в `local_settings.py` или в окружении |

## 12. Безопасность

- На рабочем сервере: `DJANGO_DEBUG=0`, собственный `DJANGO_SECRET_KEY`, точный список `DJANGO_ALLOWED_HOSTS`, доступ только по HTTPS — через страницу входа передаётся пароль домена.
- Задайте отдельный `INTEGRATIONS_ENCRYPTION_KEY` (`python -c "from cryptography.fernet import Fernet; print(Fernet.generate_key().decode())"`). Пока он не задан, ключ шифрования выводится из `DJANGO_SECRET_KEY`. Смена любого из этих ключей делает сохранённые пароли нечитаемыми — подключения, каталог и почтовый сервер придётся настроить заново.
- Не отключайте проверку сертификатов (`AD_AUTH_VERIFY_CERT`, «Проверять сертификат» у каталога и почтового сервера) на рабочем сервере: без неё подлинность сервера, которому передаётся пароль, не проверяется.
- Файлы `.env`, `local_settings.py`, `db.sqlite3` и каталог `media/` не должны быть доступны через веб-сервер и не попадают в git.
- Учётной записи для адресной книги достаточно права чтения каталога; учётной записи почтового сервера — права отправки от своего адреса.
- Неудачные попытки входа учитываются политикой блокировки домена.
